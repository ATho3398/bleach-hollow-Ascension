# 자동 진행 규칙 (가벼운 버전)

football 프로젝트의 자동화를 줄여서 가져왔다. 세션은 **마스터 세션**과 **코드 세션** 둘뿐이다. 엔진 관리자·UI 보고·fix 전용 세션은 두지 않는다.

## 0. 공통
- 모든 답변은 한국어, 맨 끝에 `명령 시각 / 답변 시각 / 걸린 시간`(KST, `TZ=Asia/Seoul date`). 세션 간 메시지와 docs/dev-log.md 보고에도 붙인다.
- 사용자 결정이 필요한 질문은 3~4개씩 추천안과 함께 묻고, 답이 없으면 추천안으로 진행한 뒤 보고한다.
- 환경 변수·비밀값은 레포에 적지 않는다(공개 레포).

## 1. 모델 선택 (사용자 확정 2026-10-18, 2026-10-19 갱신)
- **2026-10-19 사용자 허용: 고도화 단계부터 코드 세션은 Opus 5.5(`claude-opus-5-5`)로 연다.** 아래 Sonnet 기본 규칙보다 우선한다. 단 **화면 배치·문구·아이콘·CSS 같은 UI 위주 작업은 Sonnet**, 엔진·전투 로직·버그 원인 추적·세이브 구조 변경이 섞이면 Opus(마스터 판단).
- **기본은 Sonnet**(`.claude/settings.json`). 마스터 세션과 코드 세션 모두 Sonnet으로 시작한다.
- **Opus로 올리는 때**: ① 같은 문제로 Sonnet이 2번 실패 ② 여러 모듈이 얽힌 구조 변경(세이브 구조, 핵심 시스템 재설계) ③ 원인을 못 찾은 이상 동작. 올릴 때는 그 작업 한 덩어리만 Opus로 하고, 끝나면 Sonnet으로 돌아온다.
- Opus 사용은 docs/dev-log.md 소절에 이유를 한 줄 적는다.

- **2026-10-20 사용자 지시(Max 20 결제, 이번 달 최대 활용)**: 원문 "오키 잘 줄였고, 나 지금 맥스20결제해서, 이번달 안에 최대한 뽕 뽑아야하거든? 병렬로 돌리는거 할수있는만큼 돌리고, 오푸스 쓸 때 고속모드로 돌려버리고, 게임 내 밸런스 조절할 때 페이블 돌려도 돼."
  - **병렬 우선**: 영역이 겹치지 않는 코드 세션을 동시에 3~4개 돌린다. 각 세션에 패치 번호(C.n)를 미리 배정하고, 손댈 파일 영역을 지시에 적는다. 푸시 전 `git pull --rebase`(충돌은 자기 쪽에서 해결), `PATCH_LABEL`은 main 에 있는 값과 자기 번호 중 큰 것, GDD 버전은 pull 후 최신+1.
  - **밸런스 조절 = Fable 5.1**(`claude-fable-5-1`) 허용.
  - **고속 모드(Opus fast)**: 구독 한도가 아니라 별도 사용 크레딧(추가 결제)에서 빠져서 사용자 확인 대기. 확인되면 Opus 세션은 시작 때 켠다(중간에 켜면 전체 컨텍스트가 다시 과금).
  - 6장 절약 규칙 중 **읽기 최소화·캡처 1배·테스트 범위**는 속도에도 좋아서 유지한다. 마스터 교체 기준은 다시 50만·15달러(컨텍스트 품질 기준).

## 2. 단계 흐름
1. **마스터 세션**: 기획 담당. 코드를 건드리지 않고 `docs/`만 고친다. 단계 지시를 쓰고 코드 세션을 연다. 끝난 세션은 제목 앞에 `DONE_`를 붙인다(할 일을 마쳤거나 후임에게 넘겨서 다시 손대지 않는 세션이라는 표시. "draft"는 초안처럼 읽혀서 쓰지 않는다).
2. **코드 세션**: 구현 → 검증 → 배포 → docs/dev-log.md 보고.
   - **검증(푸시 전 필수)**: CI와 같은 순서로 `npm ci` 상태에서 `typecheck → test → balance:check → build`를 자기 세션에서 모두 통과시킨다. 통과 못 하면 푸시하지 않는다. 문서만 바뀐 커밋은 재검증하지 않는다.
   - **푸시 전 main 확인**: main 최신 CI가 빨간불이면 그 위에 올리지 않는다.
   - **푸시 후**: CI를 기다리지 않고 마스터 세션에 완료 보고하고 턴을 끝낸다. CI 확인은 마스터가 다음 점검 때 한다(코드 세션의 25분 뒤 `send_later` 자기 점검은 2026-10-20 폐지 — 사용량 절약). 실패하면 마스터가 같은 세션에 send_message 로 고치라고 보낸다.
3. **문서만 바뀌는 푸시**(`docs/**`)는 배포를 시작하지 않는다(워크플로 `paths-ignore`). 마스터 세션은 문서를 자기 브랜치에만 올리고, main 반영은 코드 세션이 배포할 때 병합한다.

## 3. 막혔을 때 (코드 세션)
- 질문하며 멈추지 않는다. 기획서 기본값으로 진행하고 판단과 이유를 docs/dev-log.md에 "기획서 값 / 실제 값 / 이유"로 적는다.
- 밸런스 목표는 조정 3회까지. 안 되면 현재 값을 유지하고 "목표 미달"로 기록한 뒤 다음으로 간다.
- 테스트를 지우거나 건너뛰어서 통과시키지 않는다. 새 기능에는 테스트를 추가한다.
- 테스트가 3회 시도로 안 풀리면 main 에 푸시하지 않고 작업 브랜치에만 남기고 원인을 docs/dev-log.md에 적은 뒤 마스터 세션에 알린다(깨진 상태를 배포하지 않는다).
- 위 "막힘"이 Sonnet으로 2번 실패한 것이면 1번의 규칙대로 Opus로 올려 1회 더 시도한다. 그래도 안 되면 미해결로 기록하고 다음 단계로 간다(그 문제 위에서만 가능한 작업이면 멈추고 사용자에게 묻는다).

## 4. 마스터 세션 교체
- 컨텍스트 30만 토큰 또는 비용 10달러 중 먼저 닿으면(2026-10-20 50만·15달러에서 낮춤 — 마스터는 턴마다 컨텍스트 전체를 다시 읽어서 컨텍스트가 클수록 턴 값이 비싸다): 기획서 13장 "현재 상태"를 갱신(인수인계 겸용) → 새 마스터 세션 생성 → 지금 세션 제목 앞에 `DONE_`. 세션 깊이는 `get_session`의 `lineage`로 보고, 7 이상이면 사용자에게 앱에서 직접 열어 달라고 요청한다.
- **세션 제목(사용자 확정 2026-10-18)**: 마스터 `블리치_마스터<글자>_<내용 요약>`(예 `블리치_마스터A_프로토타입 총괄`, 다음은 `B`), 코드 `블리치_코딩<번호>_<내용 요약>`(예 `블리치_코딩1_매치3 전투 코어`). 끝나면 `DONE_블리치_…`.

- **교체 체크리스트(빠짐 방지)**: ① 13장 "현재 상태" 갱신 ② 새 마스터 생성 ③ **이전 마스터 제목 앞 `DONE_`(새 마스터가 인수 직후 바로 한다)** ④ 진행 중인 코드 세션이 있으면 보고처를 새 마스터로 안내(막히면 코드 세션이 이미 끝났는지 먼저 확인) ⑤ 사용자에게 인수 보고.

- **자율 진행 원칙(사용자 지시 2026-10-19, 최우선)**: 사용자가 방향을 준 작업은 세부 설계(이름·수치·규칙 틈)를 마스터가 **추천안으로 정하고 기획서에 반영한 뒤 바로 코드 세션을 열어 진행**한다. 질문하려고 멈추지 않는다(텍스트·수치는 나중에 바꾸기 싸다). 질문은 보고 끝에 "이렇게 정했다, 바꾸려면 말하라"로만 남긴다. 사용자가 자고 있어도 끊기지 않게, 코드 세션 완료 보고 → 다음 세션 생성을 연달아 한다. 진짜로 멈추는 경우는 ① 치명 버그가 안 풀림 ② 배포 2회 연속 실패 ③ 사용자 자료(그림 등)가 있어야만 가능한 작업 ④ 되돌리기 어려운 파괴적 작업뿐이다. 멈추면 Priority 5 폰 알림.
- **연속 진행 장치**: 코드 세션을 열 때마다 마스터는 `send_later`로 약 60분 뒤 자기 점검을 1개만 예약하고(완료 보고가 오면 어차피 깨어나므로 보험용, 2026-10-20 40분→60분)(보고가 안 오거나 놓쳤을 때 대비), 깨어나면 ReadNotifications → 완료면 다음 단계 세션 생성.

- **사용자 지시 누락 방지(2026-10-20, 블록 이름 누락 사고 후)**: 사용자가 패치·불만을 말하면 마스터는 ① **원문을 그대로** 기획서 해당 장에 인용해 적고(해석·요약만 적지 않는다) ② 코드 세션 지시에도 원문을 붙이고 ③ 완료 보고를 받으면 **새 세이브 캡처로 사용자가 말한 그 화면이 실제로 바뀌었는지** 직접 확인한다. 같은 불만이 두 번 나오면 지난 해석이 틀린 것으로 보고 원인을 처음부터 다시 찾는다.

## 5. 사람이 끼는 곳
- **위임(사용자 지시 2026-10-18)**: 사용자는 전투 시스템 세부를 판단하기 어려워 마스터에게 맡겼다. **하기로 한 범위(프로토타입 P1~P3)에서 선택지가 생기면 마스터가 추천안으로 정하고 멈추지 않는다.** 사용자에게는 결정 사항을 보고만 한다(질문으로 막지 않는다). 코드 세션이 올린 질문도 마스터가 추천안으로 답한다.
- **예외(여전히 사용자에게 묻는다)**: 기획서 11장 [미정] 중 프로토타입 범위 밖인 것(11-2 진화 조건, 11-5 해방 변주, 11-6 등급전 룰, 11-7 히든 조건, 11-8 두 버전 연결, 11-9 아트·UI)과 방향을 바꾸는 큰 결정. 이런 건 해당 단계에 들어가기 전에 모아서 추천안과 함께 묻는다.
- 기본은 끝까지 자동 진행. 멈추는 경우: 사용자가 멈추라고 할 때, 치명 버그가 안 풀릴 때, 다음 단계가 미해결 문제 위에서만 가능할 때.
- 알림(폰 등)은 필요할 때 사용자와 정해서 추가한다. 지금은 없다.

## 6. 사용량 절약 (사용자 지시 2026-10-20 "블리치 프로젝트에서 줄일 수 있는 방법 적용시켜")
사용량 대부분은 ① 코드 세션 온보딩 때 큰 문서 읽기 ② 캡처 이미지 보기 ③ 컨텍스트가 커진 세션의 턴 반복이다. 아래를 모든 세션이 지킨다.

**코드 세션**
1. **문서는 필요한 곳만 읽는다.** `docs/GDD.md`(약 30만 자)는 지시에 적힌 장만 `grep -n`으로 위치를 찾아 범위로 읽는다. 전체 읽기 금지. `docs/dev-log.md`는 최근 소절 1~2개만(형식 참고용). C.0~C.59는 `docs/dev-log-archive.md`에 있고 필요할 때만 grep.
2. **코드도 필요한 파일만.** 큰 파일은 grep으로 위치를 찾은 뒤 그 부분만 읽는다. 폴더 전체 훑기는 Explore 같은 하위 에이전트에 맡기지 말고 grep 한두 번으로 끝낸다.
3. **테스트는 작업 중엔 관련 파일만**(`npx vitest run tests/<파일>`), 전체 `npm test`·typecheck·balance:check·build는 푸시 전 1회.
4. **캡처는 1배(deviceScaleFactor 1), 지시에 적힌 장면만, 10장 이내.** 자기 확인으로 직접 열어 보는 건 핵심 3~4장. 같은 장면을 고칠 때마다 다시 찍지 않는다(마지막에 한 번).
5. **dev-log 보고는 짧게**(소절 30줄 안팎): 사용자 원문·바꾼 것·기획서 값/실제 값/이유·테스트 수·캡처 목록. 긴 좌표·proof 내용은 proof.json에만.
6. 푸시 후 CI 자기 점검 없음(2장 참조). 완료 보고 뒤 바로 턴 종료.

**마스터 세션**
7. **작은 일은 묶어서 한 세션.** 사용자 요청이 짧은 수정 여러 개면 모아서 한 코드 세션에 보낸다. 작은 후속은 끝난 같은 세션에 이어 보내되, **그 세션 컨텍스트가 30만을 넘었으면 새 세션**(큰 컨텍스트에 이어 보내면 턴마다 비싸다).
8. **모델**: UI·문구·CSS·그림 넣기 = Sonnet, 엔진·세이브·밸런스·원인 모를 버그만 Opus(1장 그대로).
9. **코드 세션 지시는 짧고 정확하게**: 읽을 GDD 장 번호·대상 파일·캡처 장면 목록을 지시에 적어 탐색을 줄인다. 사용자 원문은 그대로 붙인다(누락 방지 규칙은 절약보다 우선).
10. **다른 세션 확인은 `get_session`의 요약으로.** `list_events`는 꼭 필요할 때만 `kinds`와 작은 `limit`으로(캡처가 든 세션은 결과가 수백만 자).
11. **캡처 확인은 사용자가 말한 장면 위주 4~6장.** 나머지는 proof.json·보고로 확인.
12. 마스터 교체 기준: Max 20 기간에는 50만·15달러(1장 참조).

## 폰 알림 (ntfy, 사용자 요청 2026-10-18)
- football 프로젝트와 같은 ntfy 방식. 주제 이름은 환경 변수 `NTFY_TOPIC`(레포에 적지 않는다, 없으면 사용자에게 받는다). 제목 앞에 `[블리치]`를 붙여 football 알림과 구분한다.
- **보낼 때(마스터 세션)**: ① 코드 세션의 패치 완료 보고를 받았을 때(Priority 3, 예 "C.26 완료 · T-2 · 테스트 n") ② 자동 진행이 멈춤·사용자 결정 필요·배포 2회 연속 실패(Priority 5).
- 보내는 법: `curl -s -H "Title: [블리치] 제목" -H "Priority: 3" -H "Tags: video_game" -d "본문" https://ntfy.sh/$NTFY_TOPIC` (429면 20초 뒤 최대 3번 재시도). 환경 변수는 세션 시작 때만 읽히므로 없는 세션에서는 사용자에게 알린다.
